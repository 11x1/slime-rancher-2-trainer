# ui/ notes

The settings UI has two independent parts. `core/core.cpp` calls `sr2::ui::StartOptionsTab()` and then `sr2::ui::StartOverlay()` on the worker thread, after the modules are set up. Either can fail on its own (logs the reason, returns `false`). The overlay is the guaranteed way to change settings. Before the modules are set up, `core.cpp` also calls `sr2::ui::StartModdedLabel()` (the always-on `[modded]` title-screen line, below).

Both parts draw whatever is registered in `core::settings`, grouped by module (registration order) and then by `Def::group`; neither hardcodes a module's settings. Values are written only with `settings::Set`, never into the game's save or options file. `settings_view.cpp` holds the shared code: grouping, snapping to `Def::step`, formatting, key names, module status lines, posted writes and the "Saved" bookkeeping.

The UI's own settings (module `ui`; never in a profile):

| key | kind | default | label |
|---|---|---|---|
| `overlay_hotkey` | Key | `VK_F8` | "Overlay hotkey" |
| `overlay_hint` | Bool | on | "Show overlay hint at startup" ("Press F8 for mod settings" top left for 10 s after the first frame) |
| `overlay_theme` | Enum | Dark | "Overlay theme": Dark / Light (also the Dark/Light tabs at the bottom of the sidebar) |

There is no automatic `ui.enabled` toggle: turning the UI off would lock you out of it.

RE for everything below: `re/ui.md` (Options menu classes, input system, CursorManager, main menu prefab, D3D11/Steam overlay) and `re/unity.md` (textures, sprites, GC handles, Cursor).

**Bridges.** One pattern for every custom page: the module copies what the page shows into a snapshot on the main thread (Sandbox ~4 Hz, Slime DJ 5 Hz, upgrades ~2 Hz) only while the page was drawn in the last ~0.6 s (`MarkViewed` each frame); the render thread reads only that copy (no game calls); the page posts `Action`s / `Op`s with `Request`, which `main_thread::Post` hands to the module's handler. Ids (items, songs) are opaque to the UI. Reuse this for any new module page.

## Overlay (`overlay.cpp`)

**Hooks** (MinHook via `core::HookManager`, module `"ui"`): `ui.dxgi_present`, `ui.dxgi_present1` (optional), `ui.dxgi_resize_buffers`, `ui.dxgi_resize_buffers1` (optional). The vtable comes from a throw-away device on a hidden window. RE: re/ui.md (D3D11 host).

**First Present.** Device + immediate context from the swap chain, HWND from `GetDesc().OutputWindow`. ImGui context with `IniFilename = nullptr` (no `imgui.ini`). Fonts: embedded Nunito Bold (body) and Fredoka SemiBold (headings), Segoe UI merged into both if installed (`fonts/README.md`). `ImGui_ImplWin32_Init`, `ImGui_ImplDX11_Init`, device handed to `slime_icons`, window subclassed (`SetWindowLongPtrW`). Presents from any other swap chain are ignored.

**Render target.** RTV created lazily from back buffer 0, released in `ResizeBuffers`. If the back buffer differs from the client area (scaled fullscreen), `io.DisplayFramebufferScale` keeps ImGui in client coordinates. Previous render targets are restored around `RenderDrawData`; the DX11 backend restores the rest.

**Threading.** Unity presents on its render thread; window messages arrive on the main thread.
- The WndProc only copies messages into a queue; the render thread replays them through `ImGui_ImplWin32_WndProcHandler`. ImGui is touched by one thread, nobody waits.
- `Platform_SetImeDataFn` is cleared.
- Writes go through `main_thread::Post` (module `OnChange` may touch Unity). The widget shows the pending value until it lands (dropped after 3 s if the dispatcher stalls).
- Shift / Ctrl / Alt: every frame the backend's own modifier events are removed from `g.InputEventsQueue` and the `GetAsyncKeyState` state is queued instead (the backend's `GetKeyState` is stale on the render thread and made Shift+wheel flicker).

**Toggling and key capture.** Both poll `GetAsyncKeyState` in Present, only while the game window is foreground. After a capture or toggle the key must be released before it counts again.
- Capture takes the next newly pressed key: any keyboard key (generic Shift/Ctrl/Alt skipped for their L/R codes; `VK_PROCESSKEY`/`VK_PACKET` ignored) or mouse 3/4/5. Left/right click are never captured; keys held when capture starts are ignored.
- Esc cancels; Backspace/Delete clears the bind (0, "(none)"; modules treat 0 as unbound). For the overlay hotkey clearing resets to F8.
- `WM_MBUTTONDOWN`/`WM_XBUTTONDOWN` are latched (`g_mouseLatch`, also while closed) so sub-frame clicks are not missed; cleared at capture start/end and every hotkey poll.
- The hotkey may be mouse 3/4/5; `HotkeyVk()` falls back to F8 for 0, 1, 2.
- While a text field has focus (`io.WantTextInput`), a hotkey that produces a character does not toggle.
- Middle click on a setting row resets it to its default (`DrawRow`); ignored while the row is disabled, a popup blocks, or that key bind is capturing.
- `KeyName`: "Mouse 1".."Mouse 5", F1..F24, fixed names for L/R modifiers, Win, Menu, Pause, Print Screen, media keys, else `GetKeyNameTextW` on the scan code (extended bit for E0 keys), fallback `VK 0x..`.

**Blocking game input while open** (`Captured()`: settings window or HUD edit mode):
1. WndProc: swallows `WM_KEY*`/`WM_CHAR` (queued for ImGui), and `WM_MOUSE*` while ImGui wants the mouse. `WM_INPUT` from the keyboard (and the mouse while ImGui wants it) gets only `DefWindowProcW`. `WM_SYSKEY*` reaches the game (Alt+F4, Alt+Enter), except Alt+Space / `SC_KEYMENU` while the window is open (`IsSystemMenuKey`), so Alt+Space opens the search instead of the system menu.
   - Mouse outside the overlay goes to the game: `io.WantCaptureMouse` of the last frame (forced on for two frames after opening; ORed with `hud_edit::WantsMouse()`) is kept in `g_imguiWantsMouse`. While false, mouse messages and raw input pass on, so game menus beside the window stay clickable. A press that went to the game also gets its release.
2. `game_input` (frame callback `ui.overlay`): disables `InputDirector._mainGame` (`InputActionMap.Disable`), re-enables on close only if it disabled it, re-asserts each tick. The `InputDirector` is cached; without one (title screen) the lookup runs at most once a second.
3. Game menus behind the overlay: while the overlay wants the mouse or a text field has focus, also disables `InputDirector._paused` and (mouse case) the EventSystem's current input module; both re-enabled as soon as the pointer leaves and on close. Caveat: if the game closed its menu while `_paused` was held off, the re-enable would turn it on in gameplay (not seen as reachable).
4. Cursor: `Cursor.lockState = None` and `Cursor.visible = true` every tick while open; on close `CursorManager.UpdateCursorLockState()` / `UpdateCursorVisibility()` re-apply the game's state (else the values seen on opening). A software cursor is drawn only if the cursor cannot be shown, the dispatcher / Cursor API is missing, or after a fault.
5. `game_input::GameMenuOpen()`: the game's `CursorManager` wants the cursor unlocked (true until the first tick). HUD edit uses it.
6. Steam overlay Shift+Tab: `SyncSteamKeyBlock` (render thread) installs our own `WH_GETMESSAGE` hook while captured (fresh on open, re-installed every 2 s so it stays newest) that turns Steam's posted "Tab down" message into `WM_NULL` and queues real Tab key-downs for ImGui (no `WM_CHAR` for Tab while open). Only Tab is handled, so a user-changed Steam shortcut still works; a Steam update could change the message. RE: re/ui.md (Steam overlay renderer). Logs: `ui: Shift+Tab block: WH_GETMESSAGE hook on window thread ...` once; on close `... dropped N Steam Tab-down message(s), passed M Tab press(es) ...` or a warning if the hook was never called; `ui: Shift+Tab block unavailable (...)`.
- Tab focus (`nav.cpp/.h`, round 11): Tab / Shift+Tab walk every control in drawing order (sidebar, theme tabs, build stamp, top-bar tabs, reset / switch / (?) / close, then the page: switches, sliders, dropdowns, key binds, buttons, sub-tabs, grid tabs, search boxes, grids, lists); Space / Enter press the focused one, the arrow keys move spatially. While the keyboard moves the focus, `IsItemHovered()` is true for the focused item, so hover looks and tooltips follow it (tooltips open at the item).
  - Every child window on the way is `ImGuiChildFlags_NavFlattened` (sidebar, main, page body, cards, item grids, Slime DJ lists, the Weather card's two halves): Tab and the arrows cross child borders, and Tab leaves a grid instead of looping inside it (round 10: "spamming shift tab only loops search and grid").
  - The menu's own drawn widgets use `nav::Button` (ImGui's `InvisibleButton` takes no focus: it is `NoNav`, which is why switches never got focus) and draw `nav::Ring` after themselves: ImGui's nav cursor colour (`tabSel`) and thickness, 4 px outside, with the widget's own rounding. ImGui's own widgets keep ImGui's ring.
  - Grids and lists are one Tab stop each (`nav::TabGroup`): the item focused last (by keyboard or click), else the first; the other items are `NoTabStop` but take arrow focus, so the arrows go tile by tile / row by row and out over the edge. Used by item grid tiles, the vacpack slot row, the Upgrades entries and the Slime DJ song, queue and playlist rows (their row buttons are `NoTabStop`, reached with Left / Right). A stop that disappears (search, tab switch) hands over to the first item next frame.
  - The Menu key or Shift+F10 on a focused tile / slot / upgrade entry opens its right-click menu (`nav::ContextKey`). Upgrades entries: Space / Enter opens the menu, + / - change the level; their drawn - / + buttons are `NoNav` (mouse only).
  - Not focusable: the row-wide click area behind a switch row (the switch is the stop), the save-state dot (no action), the Slime DJ seek bar (mouse drag only), and the search box's x (as before). Spotlight keeps its own keys (`NoNavInputs`).
  - A Tab / arrow move that scrolls the page counts as a user scroll for `KeepPageScroll` (`NavJustMovedToId`), so the saved position does not pull the page back.

**Limits.** Modules that poll `GetAsyncKeyState` themselves still see keys typed into the overlay unless they skip polling while `overlay::IsOpen()` (minimap zoom, hl2_movement, wall markers do). Without the main-thread dispatcher only the WndProc filter applies. Gamepad navigation is off (keyboard navigation is on: Tab focus above).

## Window (`menu.cpp`)

900×600 (times the scale, centred the first time), no title bar, drag by any empty spot. Built every frame from `BuildModuleViews()` and arranged by `menu_layout`. `settings::Flush()` runs when the overlay closes.

- **Sidebar:** slime logo, the categories, then Profiles and Settings, the Dark/Light tabs, and a footer: a save-state dot (amber 1.5 s after a change, then green; red when the last `sr2mods.json` write failed, `settings::LastSaveError()` in the tooltip) and the build stamp `dd/MM HH:mm · abc1234` (dimmer than dim text; shrinks, then shows `-dirty` as `*`, if it would overflow). Clicking the stamp copies the short commit (+`-dirty`; ISO build time without git) via `ImGui::SetClipboardText`; tooltip "copied!" for 1.5 s.
- **Build stamp:** `cmake/build_info.cmake` (always-out-of-date target `sr2mods_build_info`) writes `build/<Config>/generated/sr2mods_build_info.h` only when its text changes; `core/build_info.cpp` is the only includer. The startup log line uses the same stamp.
- **Tab bar:** every category has at least one tab. On the right: reset (tab back to defaults, switches excluded; on Profiles: rescan), the tab's master switch (module `enabled` or the tab's master key; tooltip says what it does), close.
- **Cards:** each `Def::group` is a card ("" = no heading), in two columns, shorter column first. Row = label left, control right: Bool → switch, Float/Int → slider snapped to `step` (Ctrl+click types), Enum → dropdown, Key → capture button. A whole Bool row is clickable (invisible button under it with `SetNextItemAllowOverlap`); its label is dimmed while off and brightens on hover.
- **Tooltips** come from `Def::tooltip`: what the control does plus at most one short line on a non-obvious condition. No hook names, field names or log details (those go in the module's `NOTES.md`).
- **Cards pages** (Misc > General, Ranch > Upgrades): one card per module with its switch in the card header; its groups get no headings, rows follow in group order. `Tab::cardHelp` gives each card switch its own tooltip. Two columns; `Tab::stacked` draws `columns[0]` full width and the next two columns side by side under it (unused since round 12).
  - **Card sections** (`Tab::sections`, `DrawCardSections`): a card module can hold other modules. Each `CardSection` is a small heading with a rule (`SectionHeading`), an optional dim note, the card module's groups named in it (grayed while the card's module is off), then each listed module as its switch row (`DrawRow` on a copy of its `enabled` def with `Tab::switchLabel` / `cardHelp`; a `settings::Lock` disables it) and its own rows (grayed while that module is off). Modules in `needCard` are also grayed while the card's module is off. Card groups no section names follow at the end. `layout::Build` counts the section modules as placed (only when their card is shown), spotlight indexes them under "<tab> > <card> > <section>".
  - **Ranch > Upgrades** (round 12, was Ranch > General with three cards): one Custom Upgrades card in the left column. Sections: **Plot upgrades** (Plot Upgrades' switch as "Tier effects", grayed while Custom Upgrades is off: its tiers exist only then), **Sell upgrades** (Sell Upgrades' switch as "Sell back for half price"; not tied to Custom Upgrades, it sells the game's own plot upgrades too), **Refinery upgrades** (a note: the vacpack and drone upgrades Custom Upgrades adds to the Fabricator, kept generic since that list grows; the Extra Tank III / IV slot keys, group "Vacpack"; Drone Price Limit's switch as "Drone station price limit", which also carries the station menu's Programs dialog; not tied to Custom Upgrades, its limits work for the session without it). Drone Price Limit was an unplaced module on Misc > General before.
- **Switched off:** cards stay visible, grayed and read-only (`BeginDisabled`), tab label dimmed; the switch stays usable. A master tab whose module is off (Speed Panel while Hl2 Movement is off) adds a note naming the module. The Options tab instead hides an off module's rows.
- **Nested options** (`settings::Def::parent` / `parentValue`, set by each module): a setting whose parent is a top-level row of the same card is drawn under it, indented on a thread line, sliding open/closed (0.22 s smoothstep). `DrawKids` draws in the card itself: rows shifted and clipped (`PushClipRect`), layout advanced by the visible part, rows fade with the slide; an unmeasured block is drawn parked and clipped for one frame; height re-measured every frame. Otherwise a setting stays in place and is hidden while its parent chain disallows it. A card with all rows hidden is left out. Labels drop the parent's name ("Autobhop hold key" → "Hold key").
- **Slider units:** `Def::unit` after the number, `Def::zeroText` at 0, `Def::displayScale` scales the shown value; the slider runs on the displayed value, Ctrl+click types the bare number. `FormatValue` applies the same rules (Options tab stepper text matches). Modules whose registration helper takes no unit call `settings::SetDisplay`.
- **Inline code:** console names (`IsConsoleName`: `sv_`, `hl2_`, `cl_`, `mp_` + `[a-z0-9_]`) are drawn in JetBrains Mono (`theme::Mono()`) on a rounded chip, as row labels and inside tooltips (`RichText`). The Options tab shows plain text.
- **Dropdowns** show a short label; the open list adds a one-line description per option (`layout::EnumTexts`: a table, else "Label (description)" is split).
- **Banners** at the top of the scroll area: version-guard warning (`version_guard::Mismatch()`), a module's FAILED status.
- **Scroll memory:** each page (category + tab) has its own body child (`##body_<category>/<tab>`) and keeps its scroll for the session (`g_pageScroll`, `KeepPageScroll`); a page shown again gets it with `SetNextWindowScroll` before `BeginChild`. Only the user moves it: a scroll clamped at the bottom below the saved position is not saved; the saved one is re-applied until the content is long enough, the user scrolls (wheel without Ctrl/Shift, or press on the scrollbar strip) or 10 s pass.
- **Locked switches:** `settings::Lock(module, key, value, reason)` pins a value (`Set` with another value is ignored everywhere). The overlay draws a pinned switch disabled with `settings::LockReason` as tooltip. Used by Custom Upgrades while a save with custom upgrades is loaded, and Sandbox while a cheated save is loaded. The Options tab does not show the lock (its row may read "Off" until rebound).
- **(?) markers:** one helper, `HelpMarker` (pixel-snapped disc, 1.5 px ring, "?" in the display font).
- **Unknown modules** get a card on Misc > General; unknown settings stay in their module's tab.
- **Settings page:** left: the `ui` settings and a status card (Options tab status, game build: "matches known build" in green with `version_guard::Status()` as tooltip, else the full status, warning colour on mismatch). Right: the **Discord Rich Presence** card (`DiscordCard`): module switch in its heading, **Show as Slime Rancher 2** (default on), and only while that is off an "Application ID" field (digits; `settings::SetString` on focus loss), the module's other rows, a Status line from `discord_bridge` (short state, colour by level, technical detail and "Next try in N s" in the tooltip), **Reconnect** and, with an own application, **Developer Portal** (`ShellExecuteW` on a short-lived thread). `layout::kDiscordModule` keeps it off Misc > General; the Options tab skips it. Key/value rows use `KeyValue` (values right-aligned; `SameLine(0,0)` + `SetCursorPosX`, because `SameLine(x)` in a group counts from the group start).

- **Speed Panel** is `hl2_movement`'s HUD group; switch `hl2_movement.momentum_hud`, locked while Hl2 Movement is off, with a (?).

**Theme** (`theme.cpp`). Flat SR2 colours: Dark (plum panels, slime pink, sky-blue selection) and Light (cream panels, white cards, same accents). `menu::SyncTheme` applies the style when `overlay_theme` or the scale changes; scale = client height / 1080, at least 1. Floating surfaces (tooltips, dropdowns, hint bars) use `popBg` / `popBorder` + `SoftShadow`.

**Theme peel.** Switching Dark/Light peels the old look off from the bottom-right (0.85 s): after rendering the click frame (old theme) `overlay.cpp` copies the back buffer (`CopyResource` into our texture, recreated on size/format change); following frames draw it cut along a moving diagonal with a flap and shadow, clipped to the window's rounded outline, following the window if dragged. Multisampled back buffer or a failed copy: switch without animation.

**Slime logo** (`slime_icons.cpp`). RE: re/ui.md "Slimepedia", re/unity.md (Texture).
- On every open a main-thread job (`Refresh()`) reads the loaded save's discovered non-largo slime entries (`PediaConfiguration` categories, fallback all `IdentifiablePediaEntry`, filtered with `PediaDirector.IsUnlocked`). Re-read each open.
- Pick: shuffled with the last pick moved to the back (never repeats with 2+). Icon = entry `get_Icon()` (virtual), else the type's `icon`; rect from `textureRect` or, for tight-packed sprites, the `uv` bounds. Texture kept by a GC handle; its D3D11 resource via the `GetNativeTexturePtr_Injected` icall under SEH, with our own COM reference taken right there on the main thread (never Unity's pointer on the render thread).
- Text: `_title` (else `localizedName`, else asset name), `_description`, then each detail's section title and text (`LocalizedString` via `GetLocalizedString` after `IsEmpty`, rich-text stripped). Hover shows `EntryTooltip` (wrapped at 360 px).
- Threading: a `Snapshot` under a mutex; the render thread keeps one SRV per native texture (typeless → UNORM; sRGB formats get a small pixel shader via an `ImDrawList` callback). Between an open and the new snapshot (≤ 0.5 s) the logo area stays empty.
- Default: the game's Pink Slime icon (`SlimeDefinition` named `Pink`) when no save is loaded or nothing readable is discovered (works on the title screen; no tooltip). Last resort: the drawn `DrawSlimeFallback` (lookup failed, no dispatcher, fault mode).
- Unverified in game: UV orientation (if upside down swap `uv0.y`/`uv1.y` in `Sync()`), the tight-packed UV path, that the category walk finds every slime.

**Search** (`spotlight.cpp`). Ctrl+Space or Alt+Space while the window is open: a box centred 84 px below the window top (580 px wide), window dimmed (`scrim`), floating surface, results, footer keycaps (Up Down select, Enter open, Tab switch, Esc close). The chord again, Esc or a click outside closes it; it does not open over a modal (`GetTopMostPopupModal`) and starts closed on each overlay open.
- Implementation: root `BeginPopupModal` with `NoNavInputs`, own dim off, backdrop/shadow/box drawn into channel 0 after the content; keeps keyboard focus (`SetKeyboardFocusHere`); keys read with `IsKeyPressed`.
- Index (built on open from `BuildModuleViews` + `layout::Build`): one entry per page and per setting the page shows (first place wins; HUD placement = one "Position and size" entry), with title, breadcrumb, category icon and searched-only text (tooltip, enum options, `PageKeywords(tab)` for custom pages).
- Ranking: every query word must match; title prefix 100, word start 70, anywhere 40, breadcrumb 30/15, hidden 10/6, fuzzy title 12 ("plupg" → "Plot Upgrades"); +40 whole title, +50 multi-word title start, +5 pages; ties: shorter title, then index order. At most 8.
- Open: switches page; `PulseRow` finds the row while drawing (`DrawRow`, `DrawMoveRow`, card / nested header switches); after two frames `ScrollToHighlight` puts it at 30 % of the page (stored as the page scroll), then it pulses twice (1.6 s). Hidden settings pulse the nearest shown ancestor; never-drawn settings (theme) just open the page; gives up after 1 s. Log: `ui: search "<query>" -> <title> (<breadcrumb>)`.
- Switch in place (Tab or the row switch) only when allowed: not locked, `Visible`, never Sandbox's switch. Log: `ui: search: <module>.<key> = on/off`.
- Unverified in game: Alt+Space vs. menu mode, Ctrl+Space in a text field, scroll landing on long pages.

**Profiles page** (`core/profiles.h`; file format in the README). Left card lists profiles: ACTIVE, MODIFIED (`profiles::IsModified()`, cached 250 ms), BROKEN badges; hover = description or parse error; double-click loads. **Load** posts the apply to the main thread ("Loading..." then the result). **Save** (confirm modal, keeps description), **Save as...** (name + description; existing name → "Overwrite", Enter never confirms an overwrite), **Rename** (clash needs "Overwrite"), **Delete** (modal). **Open folder**: `ShellExecuteW` on a short-lived thread (shell32 delay-loaded), fallback `explorer.exe` via `CreateProcessW`. ## HUD edit mode (`hud_edit.cpp`)

One edit mode for `Element::Minimap` (`minimap.pos_x`, `pos_y`, `size`: edge length 10-50 % of screen height) and `Element::SpeedPanel` (`hl2_movement.momentum_hud_x`, `_y`, `_size`: font size 0.8-8 % of screen height); each is a table row in `hud_edit.cpp`.

**Placement.** x / y = percent of the free space (screen minus element; 0 = left/top edge, 100 = right/bottom; `ToPx` / `ToPct`), size = percent of screen height. Resolution independent. The minimap sets anchors = pivot = (x/100, 1 - y/100) with zero anchored position. The Speed Panel box is `kBoxW` (3.2) font sizes wide, `kLine` (1.2) high plus `kBarH` (0.25) and `kDetailsH` (0.9) (`momentum_hud.h`); texts centred, so the box does not depend on font metrics.

**Starting.** **Move** calls `Begin(element)`, or drag the element while the settings window is open (`Hover`, called before `menu::Draw`): over its box (6 px margin, outside overlay windows, no popup or capture) it gets a dashed outline, a "Drag to move the minimap" pill and the move cursor; a press plus a drag past ImGui's threshold (≥ 4 px at 1080p) starts edit mode with the drag running. The Speed Panel is tested first; elements whose module is off (`settings::Visible` on the x key) are skipped; hidden elements count. `WantsMouse()` keeps press, drag and raw input from the game. The overlay closes the window when `Active()`. Edit mode keeps input like the open window (`IsOpen()` true).
- Only while the settings window is open, and not while a game menu is open behind it (`game_input::GameMenuOpen()`): then `Hover` gets `allowed = false` and **Move** is disabled ("Close the game's menu first ...").

**Controls** (`hud_edit::Draw`, foreground draw list): long-dashed outline 6 px outside with corner handles. Help bar at top centre (16 px down, 44 px high, 8 px radius, theme colours, soft shadow): element name (Fredoka), keycap hints (Drag move, Corner resize, Alt from the centre, Shift equal gaps; Alt/Shift dropped first when too wide), `Esc` X and `Enter` check buttons; fades to 35 % while the element is dragged under it. Click order: bar buttons, corners, inside, bar, outside (keep).
- Drag inside: move; snaps to the horizontal centre within 12 px (dashed guide). Shift: the gap on the drag axis becomes equal to the other gap of the nearest corner.
- Corner: resize with the opposite corner fixed; Alt: around the centre; size follows the larger axis, clamped to range and screen.
- Enter / check / click outside keeps (three `Write`s, snapped to 0.01); Esc / X / the overlay hotkey cancels. The settings window reopens on its page.

**Live preview.** `Preview(element, out)` (any thread) returns the dragged placement and, after a keep, until the settings match (≤ 1.5 s). The minimap re-runs `ApplyLayout` when it differs and ignores its "hide while a menu is open" rule while edited. The Speed Panel is drawn while edited with a sample speed (320), full opacity.

**Migration** (once, when the new keys were never saved and an old one was): Speed Panel `momentum_hud_y_offset` / `momentum_hud_scale` → x = 50, size = 1.597 % × scale, same top edge (at registration); minimap `position` + `offset_x` / `offset_y` → same edge (at its first layout, needs the canvas aspect). Old keys stay in `sr2mods.json`, unused.

**Unverified in game:** minimap anchor placement, input capture during edit mode, Alt-resize, migrations, help bar in both themes, drag to edit.

## Options tab (`options_tab.cpp`)

**Approach: inject data, not cloned UI.** The Options menu is data-driven (`OptionsConfiguration` → `OptionsItemCategory` = tab → `OptionsItemDefinition` = row with its `_controlPrefab`). Injected data objects get the native look, selection, details panel and gamepad navigation from the game's own adapters. All lookups are by name; `StartOptionsTab` refuses to install if two hook targets share an address (folded). RE: re/ui.md "Options menu".

| hook | role |
|---|---|
| `OptionsUIRoot.BindCategories` | before the original: pick templates (first non-conditional, platform-agnostic Toggle and ScriptedValueRange definition, a category), build or update one cloned definition per setting and the row models, append the Mods category to `config.items` (lands after the stock tabs, before About); after: remove it again. Injected only if at least one row model exists |
| `OptionsViewModel.GetOptionsItemsForCategory` | for Mods: an `OptionsItemModel[]` built with `il2cpp_object_new` + the `PresetOptionsItemModel(def)` ctor (not `CreateOptionItemModel`); never added to the game's `OptionsModel`, so nothing reaches the game's settings file. Never empty |
| `Toggle/ScriptedValueRangeOptionDefinition.ApplyPresetSelection` | for our definitions the original never runs; value from the game's mapping (toggle "on" = preset matching `_positiveOption`; range `GetValueForIndex`) written with `settings::Set` |
| `CategoryTabViewHolder.BindData`, `OptionsItemViewHolder.BindData`, `OptionsPresetSelector.OnSelectionChanged`, `OptionsDetailsView.BindData`, `LocalizeStringEvent.UpdateString` | localization bypass: BindData hooks register the view's LSE with our text (keyed by object + `m_CachedPtr`, released on rebind); the `UpdateString` hook substitutes it, so paged / recycled / async / locale changes all show our label. Also the sink for `core/text_override` (modules' cloned `LocalizedString`s). Texts: tab "Mods"; label = module name for the master toggle, else the `Def` label (indented); value "On"/"Off", number or enum label; details = tooltip + module status + version warning |
| `OptionsUIRoot.BindItemCategory` (optional) | empty tab details "Mods: settings for sr2mods" |
| `OptionsItemViewHolder.Activate` (optional) | a row click on our toggle steps it with `NextSetting`/`PreviousSetting` (a toggle's selector is not "activatable"). Unverified that the row click is `Activate` |

**Cloned definitions** (`Object.Instantiate` of the template): unique `_referenceId` `sr2mods.<module>.<key>`, a private `ScriptedBool`/`ScriptedFloat` (the template's setting is never written), `_applyImmediately` on, `_requireConfirmation` / `_showCondition` / `_normalizeOutputValue` cleared, `DontUnloadUnusedAsset`, GC-handle pinned. Floats, Ints and Enums map onto a stepper (`min`/`max`/`step`; Enums 0..n-1 with wrap; step coarsened on the `Def` grid above 201 positions). Key settings stay overlay-only.

**Child rows.** `BuildModels` lists rows where `settings::Visible` is true (master row always). Hidden rows keep their definition and `g_rowByDef` entry. When a parent row changes (`Row::isParent`), the value is already written (apply-immediately chain), and `ScheduleRefresh` posts one job that finds the `OptionsUIRoot` showing the Mods tab (several may be loaded; warns with the list if none matches, ≤ 5 per session) and calls `BindItemCategory(Mods)`. Around that rebind it keeps the user's place: saves the list scroll (`ScrollArea._scrollPosition`, fallback `ScrollRect`; which one is logged once), rebinds, selects the changed row with `AdapterView.SelectItem`, moves the game's UI focus to that row if focus was in the list or dead (`FocusManager.SetFocus`), restores the scroll, and settles for 6 ticks (fresh lookups, nothing held). Each missing piece is skipped and logged once. Why focus matters: the rebind destroys row controls; a dead focus made Back do nothing and the Options menu could not be closed.

**No save/revert prompt.** After every change of our rows `CommitModsSelections` calls `set_CurrentPresetIndex(TempPresetIndex)` on our models with unsaved selections, so `SaveOrRevert` never asks about already-saved values. Game rows are untouched.

**Value flow** is the game's own: selector → temp value → (apply-immediately) `ApplyPresetSelection` → our hook → `settings::Set`.

**Known gaps:** no profile row (use the overlay); the game's "reset category to default" re-applies current values (`_defaultValue` holds them; use the overlay's reset); the Mods tab icon is `mod_icons::Get("mods_tab", stock)` with a stock category icon (control/input/gameplay/accessibility/other, else About) as fallback and size reference.

**Failures and fault policy.** Every hook body runs in SEH + try/catch; each row has its own SEH frame (`row m.k skipped ... at step '<step>'`); errors log `DISABLED for this session: <why> at step '<step>' (row m.k) in <hook>` and the tab turns itself off; while disabled every Options open logs why. A native exception anywhere (hook or game code via `il::Invoke`) calls `il::MarkFault`: from then on every options hook passes straight through and no game method is called (`game_input` stops too). Two exceptions by design: `GetOptionsItemsForCategory` returns the cached, pinned non-empty model array for an already-bound Mods tab (no game calls), and our definitions never reach the original `ApplyPresetSelection`. After a fault or disable the next Options open does not inject the tab. Side effect: a game row view that showed one of ours may keep our label until the menu reopens. Injection reruns on every `BindCategories`; cached objects are checked with `IsAlive`. GC handles from `il::Keep` are pointer-sized and never freed for process-lifetime assets.

## Detour guarding (all ui detours)

Game code (the original) always runs outside the guard; after a fault each detour is a pure pass-through.

| detour | guard |
|---|---|
| Options tab (9 hooks + 2 optional) | `Guarded()`: SEH + try/catch, `il::MarkFault`; `UpdateString` has its own SEH lookup |
| `Present` / `Present1` | `OnPresentGuarded` |
| `ResizeBuffers` / `ResizeBuffers1` | `ReleaseRtvGuarded` (still releases our RTV after a fault: DXGI needs it) |
| `WndProc` | `WndFilterGuarded` |
| main-thread tick (`game_input`) | stops on `il::AnyFault()` |
| `[modded]` label | `DetourGuard` with fault name `modded_label` |

The overlay guards log code, faulting instruction as `module+offset` (`core::DescribeAddress`; use the build's PDB) and the AV access: `ui: native exception 0xC0000005 in overlay Present at version.dll+0x1234 (reading 0x...) - overlay disabled`. They are a last resort; a fault is a bug.

`core::DetourGuard` is deliberately not used for the options tab: on a fault it disables the module's hooks at the next tick, and removing the `GetOptionsItemsForCategory` interception while a Mods tab is bound brings back the empty-list ArgumentOutOfRange; and all ui hooks share HookManager module `"ui"`, so a tab fault would unhook the overlay too.

**ImGui checks.** `IM_ASSERT` stays compiled in: `imconfig.h` sends failures to `Sr2ImGuiAssertFailed` (`overlay.cpp`), logged once per check with expression, ImGui file:line and the call stack as `module+offset` (`ui: ImGui check failed: ... ; called from VERSION.dll+0x... < ...`), at most 64 checks per session; ImGui then continues as in Release. Real checks in `imgui_draw.cpp` (marked `sr2mods:`): `ImFont::GetFontBaked` clamps size to 1..512 and density to (0, 64]; `ImFontAtlasPackAddRect` refuses width/height ≤ 0 or > 0xFFFF (stb_rect_pack read through null: the Sandbox page crash); the stb_truetype loader skips inverted glyph boxes and the baked "..." without atlas rectangles.

## [modded] title-screen label (`modded_label.cpp`)

Whenever the mod is loaded, the title screen shows **`[modded]`** at the bottom left, where `support.slimerancher.com` was (the URL moves up a row). Not a module: no setting, cannot be turned off. RE: re/ui.md (MainMenuLandingRootUI prefab).
- **Start:** `StartModdedLabel()` runs before `ModuleManager::SetupAll` (skipped only if the core GC handle self-test failed): resolves names, installs the post-hook `ui.main_menu_on_enable` on `MainMenuLandingRootUI.OnEnable` (module `"ui"`, never switched off; installed even if the label's names failed, for the listener), adds frame callback `ui.modded_label` and posts one `FindObjectOfType` for a menu already up.
- **One lookup per menu:** the post-hook only takes a GC handle; the next frame does one `Transform.Find` to `SupportLabel` and `Instantiate`s it into the same layout group (last child = bottom row), named `sr2mods_ModdedLabel`, its `LocalizeStringEvent` disabled (`LocalizeFontEvent` kept), text `[modded]` re-set for 10 frames. The clone dies with the menu; re-enabling the menu does nothing while it lives. No per-frame scans.
- **Shared hook:** `quick_start` registers via `modded_label::SetMenuEnableListener` (one hook per target in MinHook). The detour runs the original, the label logic, then the listener (outside the label's guard, in `quick_start`'s own `DetourGuard`).
- **Safety:** a fault turns only the label off; the hook keeps passing through and calling the listener. Handles freed on the main thread outside hooks.
- **Log:** `ui: modded label: "[modded]" added below the support URL ...` once per launch; `ui: modded label: unavailable: ...` if a name is missing.

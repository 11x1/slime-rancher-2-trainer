# Crash 2026-10-22 18:55:04: full map opened, SlimeRancher2.exe AV

**Verdict:** the mod caused it. The **minimap** `MapUI.Awake` detour called `il2cpp_gchandle_free` on a GC handle that had been **cut to 32 bits**. In Unity 6 / IL2CPP metadata v31, `Il2CppGCHandle` is `void*`. The deployed build declared it as `uint32_t` (in `core/il2cpp_api.h` and `core/unity.*`, and through them in `minimap/ugui.cpp` `Ref`, `g_mapUIHandle`, and the old options-tab code). Every free or get_target of a stored handle therefore passes a bogus pointer to `il2cpp::gc::GCHandle::Free`/`GetTarget`. The earlier non-fatal faults that day have the same root cause: the options tab at 18:54:31, and the minimap tick and teardown at 18:54:59.

**Managed operation at crash time:** opening the full map. The UI display system finished loading the map display scene and instantiated its prefabs. Unity then sent `Awake` to the new `MapUI` component, and our MinHook detour on `MapUI.Awake` ran. Its `g_mapUIHandle.exchange(new)` returned an older (truncated) handle, and freeing that handle crashed. Nothing on this stack is game code reacting to mod state. The fault is in our detour, and it was unguarded: it runs inside `runtime_invoke`, not under the minimap's `GuardNative`, so it went straight to Unity's crash handler.

The stale value came from an earlier `MapUI.Awake` that the tick had not drained yet. The tick drains `g_mapUIHandle` in step "map ui capture" via `TakeMapUI()`, but it was in its 5 s backoff after the 18:54:59 failure, or the same instantiate batch awoke `MapUI` twice. The exact source cannot be proven, because version.dll's .data was not captured in the dump. It does not matter for the fix: any free of a stored handle faults.

## 2. GameAssembly+0x44AF0B (the minimap fault at 18:54:59)

This is the same instruction in `il2cpp::gc::GCHandle::Free`. "reading 0x683be020" means the handle was `0x683BExxx`, again a truncated pointer.

- **Step 'ui: find HudUI'**: `hud_.Reset(FindHud())` → `Ref::Reset` → `unity::FreeGCHandle(h_)` on the stale truncated `h_`. This was caught by GuardNative.
- **"teardown failed: native exception"**: `Teardown()` calls `Ref::Reset(nullptr)` on refs holding truncated handles, which reaches the same Free and faults again.

`il2cpp_gchandle_get_target` (→ 0x44B610 `GCHandle::GetTarget`) uses the same page math (`cmp byte [page+0x20],4`), so `TakeMapUI()` would also fault.

## 3. The ArgumentOutOfRangeException (Player-prev.log line 314): options tab, not fatal, main menu

The exception came from `List<T>.get_Item` ← `OptionsUIRoot.BindOptionsDetailsView(int)` ← `OptionsUIRoot.SwapCategory(int, bool)` ← `OptionsUIRoot.SaveOrRevert(Action<T>)` ← `AdapterView<…>.SelectItem(int…)` ← category-button click ← `EventSystem.Update`.

It happened in the main menu, before "Scene Transition from MainMenuFromBoot to ConservatoryFields". This matches the mod log's 18:54:31 "ui options tab DISABLED at step 'GetItems: gchandle_free' (native AV)", which has the same truncated-handle root cause. After the fault the tab stops calling the game, but the injected "Mods" category stays in the category list while the details view has no matching entry, so `SwapCategory` indexes past the end. Unity's EventSystem caught it and logged it. It is unrelated to the fatal stack.

## 4. Responsible component

- **Root cause (core):** `core/il2cpp_api.h` declared `il2cpp_gchandle_new` as returning `uint32_t`, and `get_target`/`free` as taking `uint32_t`. `core/unity.{h,cpp}` `NewGCHandle`/`GCHandleTarget`/`FreeGCHandle` used `uint32_t` too.
- Verified by disassembly of both the **deployed** game-folder `version.dll` (age 12, sha256 `f9e8d18d…`) and `build/Release`/`dist/Release` `version.dll` (age 13, 18:59:44). In both, `sr2::core::unity::FreeGCHandle` @0x386F0 does `mov ebx, ecx … mov ecx, ebx; jmp rax`, which is the 32-bit truncation. The age-10 image that crashed shows the same behaviour.
- **Crashing caller:** minimap `MapUIAwakeDetour` (`g_mapUIHandle` + `il2cpp_gchandle_free(old)` inside a hook with no fault guard).
- **Other victims:** minimap `ugui::Ref` (every `Reset` of a used Ref, including `Teardown`), and the options tab (`GetItems` at 18:54:31).

## 5. What the owners should change

State of the source as of 19:03: `core/il2cpp_api.h` (19:01), `core/unity.*`, `modules/minimap/{module.cpp, ugui.h/.cpp}` and `ui/options_tab.cpp` now use `Il2CppGCHandle = void*` throughout. **No built binary has this fix yet.** The deployed DLL and the 18:59 Release build both still truncate, and the game session started at 18:55:52 runs the buggy DLL and can crash again the same way.

1. **Core:**
   - Keep `using Il2CppGCHandle = void*`.
   - Add `static_assert(sizeof(Il2CppGCHandle) == sizeof(void*))`.
   - Add a startup self-test: `gchandle_new(obj)` must round-trip through `get_target` and must not fit in 32 bits, otherwise disable handle users.
   - Make `NewGCHandle` and the related helpers the only path to these exports, so modules do not call `api().il2cpp_gchandle_*` directly.
2. **Minimap `MapUIAwakeDetour`:**
   - Call `g_origMapUIAwake` first.
   - Do not free inside the hook. Either store the handle and let the tick free it, or use a weak handle (`il2cpp_gchandle_new_weakref`), or just store `self` and check `IsAlive` on the main thread.
   - Wrap the il2cpp calls in SEH so a fault in a game-invoked detour cannot reach Unity's crash handler.
   - Apply the same rule to every hook detour, including the 8 options-tab hooks: guard them, and pass through on fault.
3. **Minimap `Ref`/`Teardown`:** with correct handles this is fine. Keep "reset state first", and also make `Teardown` keep going past a failing `Reset`: try each Ref separately so one bad handle does not leak the rest.
4. **Options tab:** when the tab faults or disables itself after the category was injected, remove the "Mods" category from the bound list (the code at ~line 599–605 now does `List.Remove`), or keep the details list index-consistent, so `OptionsUIRoot.BindOptionsDetailsView` never receives an out-of-range index.
5. **Release hygiene:**
   - Rebuild and redeploy only after the fix. Confirm by checking that `FreeGCHandle` in the new DLL uses `rcx`, not `ecx`.
   - Deploy `version.pdb` together with the DLL, and archive each deployed DLL+PDB pair, so the next minidump can be symbolized. This one could not be: age 10 had already been overwritten.
   - Consider making the mod log roll over (`sr2mods.prev.log`) instead of being truncated on restart. The crash-session log was lost.
